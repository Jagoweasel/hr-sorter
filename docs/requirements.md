# Техническое задание: Модуль авторизации HeadHunter (Android Spoofing)

## 1. Обзор
Цель задачи — реализовать надежную систему авторизации в HeadHunter для Go-приложения `hr-sorter`, имитирующую поведение официального мобильного приложения для Android. Это позволит обходить ограничения стандартного Web OAuth и программно перехватывать токены доступа.

## 2. Функциональные требования

### 2.1. Управление аккаунтами (Multi-accounting)
*   Поддержка привязки нескольких независимых аккаунтов HH к разным профилям в системе.
*   Каждая интеграция должна хранить свой набор токенов, cookies и уникальный User-Agent.

### 2.2. Процесс авторизации (Full-Auto Flow)
1.  **Инициализация**: Система генерирует уникальный `User-Agent` (с новым UUID) для каждой новой попытки привязки.
2.  **Эмуляция**: Запуск браузера через `playwright-go` (Chromium).
3.  **Автоматический ввод**: 
    *   Переход на страницу OAuth HH.
    *   Автоматический ввод Email/Телефона, предоставленного пользователем в Web UI.
    *   Нажатие кнопки продолжения.
4.  **Ожидание взаимодействия (State Machine)**:
    *   Если HH запрашивает OTP (код из SMS/Email) — статус интеграции переходит в `awaiting_code`, пользователю в Web UI показывается форма ввода.
    *   Если HH запрашивает пароль — статус переходит в `awaiting_password`.
    *   Если HH запрашивает капчу — изображение капчи передается на фронтенд для решения пользователем.
5.  **Перехват кода**: Система должна использовать `Request Interception` для отлова редиректа на схему `hhandroid://oauth?code=...`. Ожидание должно быть неблокирующим (race condition), чтобы избежать зависаний Playwright на кастомных протоколах.
6.  **Завершение**: Полученный `code` обменивается на `access_token` и `refresh_token` через POST-запрос к API.

### 2.3. Работа с токенами
*   **Хранение**: Сохранение токенов в таблицу `integrations` (БД SQLite).
*   **Обновление (Refresh)**: Автоматический перезапрос `access_token` при получении `403 Forbidden` от API HH, используя сохраненный `refresh_token`.

## 3. Технические требования

### 3.1. Идентификация (Spoofing)
*   **User-Agent**: Строго по формату `ru.hh.android/7.<minor>.<patch>, Device: <model>, Android OS: <version> (UUID: <uuid4>)`.
*   **Заголовки**: Для всех API запросов обязателен заголовок `X-HH-App-Active: true`.
*   **Эмуляция устройства**: Использование стандартных пресетов Playwright (например, `Pixel 7`) для параметров экрана и браузерного профиля.

### 3.2. Конфигурация
*   **Дефолтные ключи**: В коде должны быть зашиты стандартные ключи Android-приложения:
    *   `ClientID`: `HIOMIAS39CA9DICTA7JIO64LQKQJF5AGIK74G9ITJKLNEDAOH5FHS5G1JI7FOEGD`
    *   `ClientSecret`: `V9M870DE342BGHFRUJ5FTCGCUA1482AN0DI8C5TFI9ULMA89H10N60NOP8I4JMVS`
*   **Переопределение**: Возможность изменить эти ключи через переменные окружения в файле `.env` (`HH_CLIENT_ID`, `HH_CLIENT_SECRET`).

## 4. UI/UX требования
*   Никакого ввода через консоль (Stdin).
*   Все взаимодействия (ввод OTP, решение капчи) происходят через модальные окна HTMX.
*   Реализовать polling (опрос) статуса авторизации на фронтенде для мгновенного закрытия модалок при успехе.

## 5. Инфраструктура
*   Запуск в локальном окружении (Windows/Linux) с установленным Playwright. Docker на данном этапе не требуется.

## 6. Ожидаемые артефакты в коде
*   Обновленный сервис `HHAuthService`.
*   Документация в `docs/hh-auth.md` с описанием процесса настройки и переменных `.env`.
*   Миграции БД (если потребуются дополнительные поля в `integrations`).
