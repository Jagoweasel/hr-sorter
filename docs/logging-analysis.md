# Анализ текущей системы логирования (Инвентаризация)

## 1. Используемые механизмы
В проекте сейчас задействованы три разных подхода к логированию:

| Механизм | Пакет | Куда пишет | Особенности |
| :--- | :--- | :--- | :--- |
| **Custom Logger** | `internal/logger` | `os.Stdout` + SSE | Поддерживает категории (HH, TG, Sync...) и ручное управление уровнями. |
| **Standard Log** | `log` | `os.Stdout` + SSE | Используется для системных событий (DB, Main, Web) без категорий. |
| **Zap Logger** | `pkg/logger` | `os.Stdout` + Stream | Практически **не используется** в бизнес-логике. |

---

## 2. Группы логов (Категории)

### Группа A: Интеграции и Синхронизация (`internal/logger`)
*   **`HH` (HeadHunter):** Жизненный цикл сессий, запуск синхронизации, ошибки API.
*   **`TG` (Telegram):** Процесс авторизации, статус подключения, ошибки `gotd`.
*   **`SYNC`:** Детальный процесс сопоставления контактов, сохранение сообщений в БД.
*   **`MSG` (Messaging):** Отправка сообщений (тело запроса, статус ответа).
*   **`HH-NET`:** (Шумная группа) Логи сетевой активности Playwright.
*   **`TRACE`:** Максимально детальные логи (дампы данных).

### Группа B: Системные логи (`log.Printf`)
*   **`[DB]`:** Инициализация базы, миграции схем, ошибки запросов.
*   **`[Main]`:** Запуск сервисов, инициализация Playwright.
*   **`[Web]`:** Ошибки шаблонов, загрузка файлов, HTTP-запросы.

### Группа C: Специализированные логи
*   **`[HISTORY]`:** Цепочка перемещения кандидата по стадиям (метод `LogChain`).

## 3. Выявленные проблемы
1.  **Фрагментация:** Смешивание стилей в рамках одного модуля.
2.  **Потеря данных в UI:** Буфер SSE (100 строк) переполняется, отбрасывая важные логи.
3.  **Отсутствие истории:** При перезагрузке страницы UI пуст.
4.  **Слабая типизация:** Логи передаются строками, что усложняет фильтрацию и визуализацию.
